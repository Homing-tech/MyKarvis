1. 关键决策（为什么这么做）

决策结论依据
微信入口企微自建应用，而非公众号公众号强制 80/443 + 备案域名；企微允许任意端口
域名 / 备案不需要自建应用回调可直接 http://公网IP:端口/path（上游《回调URL配置指南》方案 B）
大脑实现自研轻量内核，不用 Pi4G 内存跑不动常驻 Pi 子进程
记忆存储SQLite + FTS5上千 md 检索会慢；结构化记录 + 每日 md 双写
超时处理先回 success，再异步处理并主动推送企微要求 5 秒内响应，大模型必然超时

5. 第三步：代码部署（Git + tarball 兜底）

硬约束：.env 永不入库（.gitignore 锁死，deploy/create_env.sh 同样 ignore）。
# 本地：仓库准备（防 CRLF 导致服务器报 bad interpreter）
git init -b main && git config core.autocrlf=input
git remote add origin <仓库地址> && git push -u origin main

# 服务器：一条命令部署（备份旧项目 → 停旧服务 → 拉代码 → 构建 → 自检）
curl -fsSL <脚本URL>/setup_from_git.sh -o /tmp/s.sh && sudo bash /tmp/s.sh <仓库地址> main
脚本下载务必先验真（镜像站缓存会拿到残缺旧版）：wc -c /tmp/s.sh 与仓库字节数比对 + bash -n /tmp/s.sh 语法检查。

已知坑：GitHub 镜像站（ghfast / gh-proxy / ghproxy）只转发 GET，不转发 git 的 upload-pack POST，git clone 必然全失败 → 脚本已内置 tarball GET 兜底。日志里前几个源失败属预期，不要中断。已挂镜像：gh.llkk.cc、gitclone.com。

5.1 代码迭代：本地改动 → Git → 服务器

这是「改完代码 / 改完人格」后的标准回路。人格改动只涉及 assistants/*/AGENTS.md，也走同一条路。

# ① 本地提交（在 karvis/ 目录下）
git status --short                 # 确认没有 .env / data/ 被列进来
git check-ignore -v .env           # 期望输出 .gitignore 规则，证明已忽略
git add -A && git commit -m "feat/fix/docs: <一句话说明>"
git push origin main

# ② 服务器拉取（不动 .env 与 data，脚本已内置）
sudo bash /opt/karvis/deploy/update.sh

# ③ 若改的是人格/配置而非代码，通常再重建一次即可
cd /opt/karvis && docker compose up -d --force-recreate
提交信息约定（与本次仓库保持一致，便于日后回溯）
前缀用途
feat:新能力（如新增一个助手）
fix:修 bug（如脚本 set -e 误退出）
docs:文档/人格文案（如改 AGENTS.md、补 SOP）

分支策略：单人项目直接推 main 即可；想先灰度则另开分支，把部署命令第二个参数换成分支名（setup_from_git.sh <仓库> <分支>），验证通过再合回 main。

私有仓库：脚本支持 GITHUB_TOKEN，在服务器执行前导出即可（tarball 兜底路径会用）：

export GITHUB_TOKEN=<你的token>; sudo -E bash /opt/karvis/deploy/setup_from_git.sh <仓库> main

5.2 回滚

# 方案 A（推荐）：revert 一个提交，历史干净且可追溯
git revert <坏提交hash> && git push origin main
sudo bash /opt/karvis/deploy/update.sh

# 方案 B：临时回到某个历史版本（tarball 模式无 .git 时用）
curl -fsSL https://ghfast.top/https://github.com/<用户>/<仓库>/archive/<commit>.tar.gz -o /tmp/old.tar.gz
# 解包覆盖到 /opt/karvis 后 force-recreate

5.3 Git 安全清单（每次 push 前过一遍）

若误提交过密钥：立刻去平台作废重建，仅删文件无效 —— 历史 commit 里仍然存在。
  • .gitignore 含 .env、data/、*.db（用 git check-ignore -v .env 验证）
  • git status 里没有密钥、没有聊天记录导出
  • 文档里不贴真实 Secret / AESKey（只写变量名与长度规则）

6. 第四步：凭证写入（顺序关键）

正确顺序：企微生成 Token/AESKey → 写入服务器 .env → 重建容器 → 回企微点保存回调。
反过来的话，保存时企微会立刻用 Token 验签 URL，而服务端还没配置 → 404 → 保存失败。
sudo sed -i -e 's/^WECOM_FITNESS_AGENT_ID=.*/WECOM_FITNESS_AGENT_ID=<值>/' \
  -e 's/^WECOM_FITNESS_SECRET=.*/WECOM_FITNESS_SECRET=<值>/' \
  -e 's/^WECOM_FITNESS_TOKEN=.*/WECOM_FITNESS_TOKEN=<值>/' \
  -e 's/^WECOM_FITNESS_AESKEY=.*/WECOM_FITNESS_AESKEY=<值>/' /opt/karvis/.env

sudo chmod 600 /opt/karvis/.env
grep -c '^WECOM_.*=.\+' /opt/karvis/.env      # 应为 1 + 4×应用数
改 .env 后必须重建容器：cd /opt/karvis && docker compose up -d --force-recreate（restart 不重读 env_file）。

敏感值优先用终端交互输入

read -s -p "paste: " K; echo; echo "LEN=${#K}"
sudo sed -i "s|^DEEPSEEK_API_KEY=.*|DEEPSEEK_API_KEY=$K|" /opt/karvis/.env

10. 排错表（本次实战踩过的坑，按命中率排序）

#症状真因解法
1助手回「DeepSeek API Key 无效（401）」Key 残缺：仅 sk-+20 位（标准 35 位）新建 Key；先 echo ${#K} 断言 35；终端 read -s 交互写入
2改了 .env 不生效docker restart 不重读 env_filedocker compose up -d --force-recreate
3能收消息不回复企业可信 IP 未配每应用填公网 IP（日志 60020 即此因；60020 反证 Secret 有效）
4聊天里粘的 Key 总不对长串密钥在 IM/终端往返被截断或改写服务器终端 read -s + 长度断言；或用脚本从本地文件正则取值写入
5回调保存失败「URL 验证失败」服务端未配该应用 Token/AESKey 或未重建按第 6 节顺序：写 .env → 重建 → 再保存
6网页终端多行粘贴卡 PS2反斜杠续行带 CR一律单行命令
7heredoc 写文件「假成功」粘贴丢失，No such file改单行 printf '%s\n' ... > file + grep -n | cat -A 验真
8脚本大小与仓库不符镜像站缓存旧版重下 + wc -c 比对 + bash -n
9git clone 所有镜像全失败镜像只转发 GET，不转发 upload-pack POST走 tarball 兜底（已内置，失败日志属预期）
10脚本运行到一半静默退出set -euo pipefail 下 [ cond ] && cmd 作独立语句一律改 if
11端口释放不掉直接 kill 了 docker-proxystop + rm 容器
12服务器 .env 被清空rsync --delete 未排除加 --exclude '.env'
13脚本 bad interpreterCRLF 换行本地 core.autocrlf=input，脚本保 LF
14应用在自己企微里找不到可见范围没加自己 / 微信未关注企业加可见范围 + 微信插件扫码
