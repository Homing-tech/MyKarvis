# 埼玉教练 v0.2.0 方案 · 从记事本到教练

> 状态：**已确认并实施**（v0.2.0）。决策点结论：A 做（简写解析）／B 不做（不回填历史）／C 顺带一问。
> 参考来源：[IronClaude](https://github.com/mosnicholas/iron-claude)（抄架构）、[GymCoach](https://github.com/Julien-Au/gymcoach)（抄算法）。
> 算法细节与出处见：[fitness_算法与规则出处.md](fitness_算法与规则出处.md)；自检：`python tools/test_fitness_v02.py`。

## 一、一句话结论

**只做三件 P0：训练档案、PR/1RM 追踪、渐进超负荷建议。**
这三件是连带关系——没有档案，任何个性化建议都是通用健身知识的包装；没有 PR，训练没有即时正反馈；没有渐进超负荷，教练就只是个记录员。三件做完，埼玉才从**记事本**变成**教练**。

周计划、周复盘、训练前 readiness、容量带 MEV/MRV **本次一律不做**（见第六节）。

## 三、三件 P0 的具体设计

### P0-1 · 训练档案（onboarding）

**做什么**：新增 `data/fitness/profile.md`，字段骨架：

```
目标：主目标 / 次要目标 / 训练年限
条件：训练地点 / 可用器械 / 每周频率
限制：伤病史 / 禁忌动作
基线：体重 / 主要动作当前水平
```

**放哪（关键决策）**：放 `data/fitness/profile.md`，**不放 `assistants/`**。
理由：`assistants/` 是代码层，`update.sh` 里有 `git reset --hard`，放那会被冲掉；`data/` 是 Docker volume + 备份范围，且含伤病史属私密数据，与 `_shared/profile.md` 里「健身数据属私密层」的约定一致。

**怎么填（关键决策）**：**顺带一问，不连环追问**。
教练在每次回复**末尾**追加一句提问（一次只问一组），你口语回答 → 抽取 → 写回 profile.md。
不用 IronClaude 的五阶段连环追问，理由：`_shared/profile.md` 里写了你「口语、碎片、一句话交代完」，连环追问会被无视。

**边界**：字段为空时教练照常工作，只是建议偏通用；**绝不编造档案内容**（遵循现有「不编造」硬约束）。

### P0-2 · PR / 1RM 追踪

**算法**（GymCoach 的 Epley）：

```
估算 1RM = 重量 × (1 + 次数 / 30)     例：60kg × 5 次 → 70.0kg
```

- **仅当次数 ≤ 12 才估算**，>12 记为耐力记录、不出 1RM（Epley 在高次数区误差大）
- 破 PR 判定：同动作的估算 1RM 超过历史最高 **≥ 0.5kg**（留抖动余量）
- 动作归一：由 LLM 输出简短标准名 `exercise_key`（卧推 / 深蹲 / 硬拉 / 引体 / 划船 / 肩推…），匹配时**完全相等优先**，无完全相等再取最长包含匹配（避免「卧推」误配「哑铃卧推」）

**新增表 `pr_record`**：`id, exercise_key, weight_kg, reps, est_1rm, rir, log_date, source_log_id, created_at`

**破 PR 时教练主动播报**，格式：

> 卧推 60kg×5 → 估 1RM **70.0kg**，破 PR（上次 67.1kg，+2.9kg）

### P0-3 · 渐进超负荷建议

**分工原则**：代码只负责**取数与计算**，判断规则写进 `AGENTS.md` 交给 LLM——延续本项目「改行为只改 Markdown」的设计。

代码提供历史对比（注入上下文）：

```
【卧推 · 历史】
09-02  60.0kg×5×5  RIR2  → 估 1RM 70.0
08-30  57.5kg×5×5  RIR3  → 估 1RM 67.1
08-27  57.5kg×5×5  RIR3  → 估 1RM 67.1
趋势：重量↑，RIR 由 3 降到 2
```

`AGENTS.md` 里写死决策表：

| 上次 RIR | 下次怎么调 |
|---|---|
| ≤ 2 | 上肢 +2.5kg / 下肢 +5kg |
| 3–4 | 重量不变，先加 1–2 次 |
| ≥ 5 或未填 | 重量不变，先做满目标次数 |
| 同重量同次数连续 2 次无进展 | 建议 deload（×0.9，一周）或换动作 |
| **有疼痛信号** | **不进渐进**，先减载；关节/尖锐/持续则建议就医 |

RIR 说明：记录时说「还剩 1 次余力」「还能做 2 个」即可带上；**不填也能用**，代码走「未填」分支。

## 五、预期效果

**① 档案未填时（顺带一问）**

> 你：今天练了胸，卧推 60kg 5×5
> 教练：记下了，胸 + 卧推 60kg×5×5。卧推下次上 62.5kg，RIR 控制在 2–3。另外——你训练是在健身房还是家里？有器械清单我才能排得准。

**② 破 PR 时（主动播报 + 下次建议）**

> 你：卧推 62.5 5 5 5，最后一组还剩 1 个
> 教练：卧推 62.5kg×5 → 估 1RM **73.0kg**，破 PR（上次 70.0，+3.0）。下周上 65kg，RIR 留 2–3；如果第 3 组掉到 4 次就别硬顶，退回 62.5 补次数。

**③ 查档案 / 查 PR**

> 你：我卧推到多少了
> 教练：卧推当前 1RM 估 73.0kg（09-09，62.5×5）。近三次：70.0 → 73.0，在涨。

**④ 量化收益**

| 指标 | 现在 | v0.2.0 后 |
|---|---|---|
| 建议的个性化程度 | 通用健身知识 | 基于你自己的 PR 曲线与 RIR |
| 进步的正反馈 | 无 | 破 PR 主动播报 |
| 下次练多少 | 靠感觉 | 有明确推导（重量/次数/RIR） |
| 伤病规避 | 被动（你提了才知道） | 档案里的禁忌动作长期生效 |

## 七、风险与已知边界

1. **1RM 是估算值，不是实测**，误差约 ±5%，只能看趋势、不能当绝对数字。回复里会带「估」字。
2. **历史训练记录无法回溯生成 PR**——之前 exercises 存的是字符串、无统一动作名与 RIR。PR 从 v0.2.0 上线后**新记的**开始积累。
   （可选：写一次性回填脚本，用正则从旧 `raw_input` 里抽数字补建 PR。待你确认是否要做。）
3. 动作名归一靠 LLM 输出 + 包含匹配，**同一动作的不同叫法可能被拆成两条 PR 曲线**。用久了可以在档案里维护别名表，本次不预先做。
4. 档案为空期间，建议会偏通用，这符合现有「不编造」约束，不是 bug。
5. 新增一次 LLM 抽取字段会让单次记录多耗少量 token，响应仍在秒级。

## 九、确认后的执行与验收

**执行顺序**：改代码 → `bash deploy/release.sh minor "埼玉教练：训练档案 + PR 追踪 + 渐进超负荷建议"` → 服务器更新（tarball 三步或 `update.sh`）→ `record_release.sh v0.2.0`。

**验收三件事**：

1. 发「卧推 60kg 5×5，还剩 1 个」→ 看是否计算 1RM、判定破 PR、给出下次重量
2. 发「我卧推到多少了」→ 看是否查 `pr_record` 如实回答
3. `curl http://49.235.107.213:9000/health` → `version` 应为 `0.2.0`

**回滚**：`sudo bash deploy/rollback.sh v0.1.0`（只动代码，不动训练数据）。
