# Karvis 项目管理规范

> 目标：让这个长期迭代的个人项目**版本可追溯、随时可回滚、数据在云端**。
> 适用：MVP（v0.1.0）之后的持续定制。

---

## 0. 一句话概括

**每个版本 = 一个 Git tag + 一条 CHANGELOG 记录 + 服务器 `/opt/karvis/VERSION` + 一次数据快照。**
四者齐全，这个版本才算"被记录"，也才谈得上回滚。

---

## 1. 版本管理（三层锚点）

| 层 | 载体 | 作用 | 怎么查 |
|---|---|---|---|
| 代码版本 | Git tag `vX.Y.Z` | 唯一权威来源，可检出任意历史 | `git tag -l` |
| 变更记录 | `CHANGELOG.md` | 人可读：这一版改了什么、为什么 | 直接看文件 |
| 线上版本 | 服务器 `/opt/karvis/VERSION` + `/health` | 确认线上**实际**跑的是哪一版 | `curl http://127.0.0.1:9000/health` |

`/health` 返回示例（`version` 与 `commit` 是判断发布是否生效的依据）：

```json
{"status":"ok","version":"0.1.0","commit":"747e997","agents":{"life":true,"fitness":true,"mood":true}}
```

**版本号规则（SemVer）**

| 类型 | 什么时候用 |
|---|---|
| `major` `X.0.0` | 架构变更、不兼容旧数据/旧配置 |
| `minor` `0.X.0` | 新增能力，向后兼容 |
| `patch` `0.0.X` | 修 bug、调人格文案、改文档 |

> 改 `assistants/*/AGENTS.md`（人格）也算一个 patch——人格是产品行为，改了就要留痕。

---

## 2. 分支与提交

| 场景 | 做法 |
|---|---|
| 小改动（修 bug / 改人格 / 改文档） | 直接在 `main`，走 release.sh 发 patch |
| 新功能（可能多次调试） | 开 `feat/xxx` 分支，完成后合回 `main` |
| 实验性改动 | 开 `exp/xxx`，不合并就删掉 |

**提交信息前缀**：`feat:` 新能力 ｜ `fix:` 修 bug ｜ `docs:` 文档与人格 ｜ `release:` 发布

---

## 3. 发布流程（标准四步）

```bash
# ① 本地：改代码 / 改人格
# ② 本地：把需求状态在 BACKLOG.md 里更新为 ✅

# ③ 本地：一键发布（版本号 + CHANGELOG + tag + push）
bash deploy/release.sh patch "说明这次改了什么"

# ④ 服务器：拉取 + 记录版本（脚本会打印这两行）
cd /opt/karvis && sudo bash deploy/update.sh
cd /opt/karvis && sudo bash deploy/record_release.sh v0.1.1
```

第 ④ 步末尾会打印 `/health`，**确认 `version` 是新版本号**才算发布成功。

发布前脚本会自动拦截：`.env` 进暂存区、`.env` 未被 ignore、tag 重复。**拦下来就先解决问题，不要绕过。**

---

## 4. 三级回滚

| 级别 | 场景 | 命令 | 耗时 | 数据影响 |
|---|---|---|---|---|
| **L1 镜像/代码回滚** | 新版本有问题，退回上一版 | `sudo bash deploy/rollback.sh v0.1.0` | ~2 分钟 | 无（自动先快照） |
| **L2 单次改动撤销** | 只错了一个提交 | `git revert <hash>` → 重新发布 | ~3 分钟 | 无 |
| **L3 数据恢复** | 数据被写坏 / 误删 | 见第 5 节 | ~5 分钟 | **会覆盖当前数据** |

**L1 细节**：`rollback.sh` 会先备份数据 → 下载该 tag 的 tarball → 覆盖代码（排除 `.env`/`data`/`backups`）→ 重建容器 → 打印 `/health`。
因为走 tarball，**服务器没有 `.git` 也能回滚**（这正是当初 tarball 兜底部署的附加收益）。

查历史版本：`sudo bash deploy/rollback.sh --list`（读 `deploy/releases.log`）。

---

## 5. 数据：云在哪一层

**当前架构**：数据主副本在服务器 `/opt/karvis/data`（SQLite + 每日 md），因为它需要低延迟读写；**云上的是备份副本**，不在主链路。

| 层 | 位置 | 保留 | 说明 |
|---|---|---|---|
| 主数据 | 服务器 `/opt/karvis/data` | 持续 | SQLite + `memory/*.md` 双写，人可直接读 |
| 本地快照 | 服务器 `/opt/karvis/backups` | 7 天 | 同一块盘，只防误删/写坏，**不防机器故障** |
| 云端备份 | 腾讯云 COS | 30 天 | 异地，防机器故障。需配置凭证 |

**启用云端备份**

```bash
# ① 在 /opt/karvis/.env 追加（值换成你自己的）
COS_BUCKET=xxx-1234567890
COS_REGION=ap-guangzhou
COS_SECRET_ID=AKIDxxxx
COS_SECRET_KEY=xxxx

# ② 装 coscli
wget -q https://cosbrowser.cloud.tencent.com/software/coscli/coscli-linux -O /usr/local/bin/coscli && chmod +x /usr/local/bin/coscli

# ③ 立即备份一次 + 装每日 03:00 定时任务
cd /opt/karvis && sudo bash deploy/backup.sh
cd /opt/karvis && sudo bash deploy/backup.sh --install-cron
```

COS 未配置时脚本不会失败——只做本地快照并提示。**所以可以先把定时任务装上，凭证后补。**

**恢复数据**（会覆盖当前数据，先确认）：

```bash
cd /opt/karvis
docker compose down
tar -xzf backups/karvis-data-20260909-0300.tar.gz -C /opt/karvis
docker compose up -d
```

> ⚠️ 没演练过的备份等于没有备份。建议每季度做一次恢复演练（BACKLOG B3）。

## 6. 迭代节奏建议

| 周期 | 做什么 |
|---|---|
| 随时 | 想到需求 → 记进 `BACKLOG.md`（不要只在脑子里） |
| 每周 | 挑 1–3 项做掉，攒够就发一个 patch 或 minor |
| 每月 | 过一遍 BACKLOG：优先级重排；做一次备份恢复演练 |
| 每季度 | 密钥轮换 + 依赖升级 + 看 DeepSeek 成本 |

**一条硬规则：先记 BACKLOG 再写代码。** 版本记录的价值取决于需求是否被记录，漏记的改动等于没发生过。

---

## 7. 安全红线

1. `.env` **永不入库**（脚本已强制检查；误提交过就必须去平台作废重建，删文件无效）
2. 备份**不含** `.env`（密钥不出服务器；换机器用 `deploy/create_env.sh` 重建）
3. 文档里只写变量名与长度规则，不贴真实 Secret / AESKey
4. 废弃的 API Key 及时在平台删除

## 8. 命令速查

| 想干什么 | 命令 |
|---|---|
| 发一个补丁版 | `bash deploy/release.sh patch "说明"` |
| 发一个新功能版 | `bash deploy/release.sh minor "说明"` |
| 看线上版本 | `curl -s http://127.0.0.1:9000/health` |
| 看历史发布 | `sudo bash deploy/rollback.sh --list` |
| 回滚到某版本 | `sudo bash deploy/rollback.sh v0.1.0` |
| 立即备份 | `sudo bash deploy/backup.sh` |
| 装每日备份 | `sudo bash deploy/backup.sh --install-cron` |
| 更新代码（不改版本） | `sudo bash deploy/update.sh` |
| 看运行日志 | `docker logs karvis --tail 100 -f` |

## 9. 相关文件

| 文件 | 作用 |
|---|---|
| `VERSION` | 当前版本号（被打包进镜像，`/health` 读取） |
| `CHANGELOG.md` | 每个版本改了什么 |
| `BACKLOG.md` | 需求看板（迭代入口） |
| `deploy/release.sh` | 发布（本地） |
| `deploy/record_release.sh` | 记录版本并生效（服务器） |
| `deploy/rollback.sh` | 回滚到指定版本（服务器） |
| `deploy/backup.sh` | 数据备份（服务器） |
| `deploy/update.sh` | 拉代码更新（服务器） |
| `deploy/部署SOP_可复用手册.md` | 从零部署另一套的完整 SOP |
