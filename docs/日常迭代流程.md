# 日常迭代流程速查

> 一句话：**改什么，决定走哪条路。** 不是所有改动都要重建镜像，最频繁的人格调整其实是零成本的。

## 一、主表：改什么 → 怎么发

| 改动类型 | 例子 | 本地 | 服务器 | 是否重建镜像 | 影响 |
|---|---|---|---|---|---|
| **调助手人格** | `assistants/*/AGENTS.md` 说话风格、流程 | 改完 push | 无（下次对话自动生效） | 否 | **零停机** |
| **改业务代码** | `gateway/*.py` 加功能、修 bug | `release.sh patch` | `update.sh` + `record_release.sh` | 是 | 1–2 分钟 |
| **加依赖 / 改环境** | `requirements.txt`、`Dockerfile` | `release.sh minor` | `update.sh --rebuild` + `record_release.sh` | 是 | 3–5 分钟 |
| **改配置** | `.env` 换 key、开定时推送 | 无 | 改完 `up -d --force-recreate` | 否 | ~10 秒 |
| **回滚** | 新版本有 bug | 无 | `rollback.sh v0.1.0` | 是 | ~2 分钟 |

## 二、标准四步（改代码时）

```bash
# 1. 本地改代码并自测

# 2. 本地：版本号 +1、写 CHANGELOG、打 tag、push（一条命令全做完）
bash deploy/release.sh patch "修复埼玉教练记录漏了组数"
#    结尾会打印下一步该在服务器跑什么

# 3. 服务器：拉最新代码 + 重建镜像 + 自检
cd /opt/karvis && sudo bash deploy/update.sh

# 4. 服务器：记录版本 + 打印 /health 确认
cd /opt/karvis && sudo bash deploy/record_release.sh v0.1.1
```

第 4 步会打印 `/health`，看到 `"version":"0.1.1"` 才算发布成功。**本地打了 tag ≠ 线上更新了**，这两步必须都做。

## 三、版本号三档怎么选

| 命令 | 变化 | 什么时候用 |
|---|---|---|
| `release.sh patch` | 0.1.0 → 0.1.1 | 修 bug、调提示词、小优化 |
| `release.sh minor` | 0.1.0 → 0.2.0 | 加一个新能力（如「周报推送」） |
| `release.sh major` | 0.1.0 → 1.0.0 | 架构级改动、不兼容升级 |
| `release.sh v1.0.0` | 直接指定 | 想手动指定版本时 |

## 四、调人格（最快路径，最常用）

`system_prompt()` 每次对话都重新读 `AGENTS.md`，而 `assistants/` 是 volume 挂载的——所以：

**最快做法**：直接在服务器上改，改完**发下一句话就生效**，不用重建、不用重启。

```bash
# 服务器上直接编辑（立刻生效）
sudo vi /opt/karvis/assistants/fitness/AGENTS.md

# 想试试效果？直接去企微发一句话
```

⚠️ **但必须回本地同步一次**，否则下次 `update.sh` 会把服务器上的改动覆盖掉：

```bash
# 本地把同样的改动写进 assistants/fitness/AGENTS.md 后
git add assistants/ && git commit -m "tune(fitness): 调整教练语气" && git push
```

推荐顺序：**先在本地改 → push → 服务器 `sudo bash deploy/update.sh`**，这样两边永远一致。急着验证效果时再用服务器直改 + 事后补 push。

## 五、回滚

```bash
# 看历史上发布过哪些版本
sudo bash deploy/rollback.sh --list

# 回到指定版本（回滚前会自动快照 data，回滚后自动重建镜像）
cd /opt/karvis && sudo bash deploy/rollback.sh v0.1.0
```

回滚只动代码，**不动 `data/`（你的对话记录）**，且回滚前会先快照一份到 `backups/`。

## 六、改配置（换 key / 开定时推送）

```bash
# 服务器上改 .env
sudo sed -i 's/^ENABLE_SCHEDULER=.*/ENABLE_SCHEDULER=1/' /opt/karvis/.env
sudo sed -i 's/^KARVIS_OWNER_USERID=.*/KARVIS_OWNER_USERID=你的企微账号/' /opt/karvis/.env

# 必须 force-recreate，docker restart 不会重新读取 .env
cd /opt/karvis && sudo docker compose up -d --force-recreate && sleep 6 && curl -s http://127.0.0.1:9000/health
```

## 七、数据备份（当前策略：本地快照）

暂不启用 COS 云备份，只保留本地快照（7 天轮转）：

```bash
sudo bash /opt/karvis/deploy/backup.sh
# 快照位置：/opt/karvis/backups/karvis-data-YYYYMMDD-HHMMSS.tar.gz
```

⚠️ 风险已知并接受：数据只有一份、在服务器单块盘上。盘挂了记录就没了。要上云时补 `COS_BUCKET / COS_REGION / COS_SECRET_ID / COS_SECRET_KEY` 四项到 `.env`，再 `sudo bash deploy/backup.sh --install-cron`。

## 八、三个高频坑

| 现象 | 原因 | 解决 |
|---|---|---|
| 改了代码线上没变 | `gateway/` 是打包进镜像的，只 `restart`/`--force-recreate` 不重建镜像 | 用 `update.sh`，或 `docker compose up -d --build` |
| 改了 `.env` 不生效 | 容器启动时才读 env | 必须 `--force-recreate` |
| `update.sh` 所有源拉不到 | GitHub 镜像站间歇性抽风 | 手动 tarball 三步（见 `docs` 或部署 SOP 手册 §4） |

## 九、需求管理

想到新功能先记进 `BACKLOG.md`（别急着做），排期时再从里面挑。做完的功能在 `CHANGELOG.md` 里会有记录——`release.sh` 自动写。
