埼玉教练 v0.2.0 方案 · 从记事本到教练

状态：待确认，确认后才动手写代码　|　参考：IronClaude（抄架构）· GymCoach（抄算法）
一句话结论：只做三件 P0——训练档案、PR/1RM 追踪、渐进超负荷建议。
三件是连带关系：没有档案，任何个性化建议都是通用健身知识的包装；没有 PR，训练没有即时正反馈；没有渐进超负荷，教练就只是个记录员。三件做完，埼玉才从记事本变成教练。

二、三件 P0 的具体设计

P0-1 · 训练档案（onboarding）

字段目标（主/次/训练年限）· 条件（地点/器械/每周频率）· 限制（伤病史/禁忌动作）· 基线（体重/主要动作水平）
放哪data/fitness/profile.md　不放 assistants/

理由：assistants/ 是代码层，update.sh 里有 git reset --hard，放那会被冲掉；data/ 是 Docker volume + 备份范围，且含伤病史属私密数据，与「健身数据属私密层」约定一致。

怎么填顺带一问，不连环追问——在每次回复末尾追加一句提问（一次一组），你口语回答 → 抽取 → 写回档案

不用 IronClaude 的五阶段连环追问：你的沟通风格是「口语、碎片、一句话交代完」，连环追问会被无视。
边界：字段为空时教练照常工作，只是建议偏通用；绝不编造档案内容。

P0-2 · PR / 1RM 追踪

估算 1RM = 重量 × (1 + 次数 / 30)　　例：60kg × 5 次 → 70.0kg
  • 仅当次数 ≤ 12 才估算，>12 记为耐力记录、不出 1RM（Epley 在高次数区误差大）
  • 破 PR 判定：同动作估算 1RM 超过历史最高 ≥ 0.5kg（留抖动余量）
  • 动作归一：LLM 输出简短标准名 exercise_key（卧推/深蹲/硬拉/引体/划船/肩推…），匹配时完全相等优先，无完全相等再取最长包含匹配（避免「卧推」误配「哑铃卧推」）
  • 新增表 pr_record：id, exercise_key, weight_kg, reps, est_1rm, rir, log_date, source_log_id, created_at
破 PR 时教练主动播报
卧推 60kg×5 → 估 1RM 70.0kg，破 PR（上次 67.1kg，+2.9kg）

P0-3 · 渐进超负荷建议

分工原则：代码只负责取数与计算，判断规则写进 AGENTS.md 交给 LLM——延续本项目「改行为只改 Markdown」的设计。

【卧推 · 历史】 09-02 60.0kg×5×5 RIR2 → 估 1RM 70.0 08-30 57.5kg×5×5 RIR3 → 估 1RM 67.1 08-27 57.5kg×5×5 RIR3 → 估 1RM 67.1 趋势：重量↑，RIR 由 3 降到 2
上次 RIR下次怎么调
≤ 2上肢 +2.5kg / 下肢 +5kg
3–4重量不变，先加 1–2 次
≥ 5 或未填重量不变，先做满目标次数
同重量同次数连续 2 次无进展建议 deload（×0.9，一周）或换动作
有疼痛信号不进渐进，先减载；关节/尖锐/持续则建议就医

RIR 说明：记录时说「还剩 1 次余力」「还能做 2 个」即可带上；不填也能用，代码走「未填」分支。

四、预期效果

① 档案未填时（顺带一问）
你：今天练了胸，卧推 60kg 5×5
教练：记下了，胸 + 卧推 60kg×5×5。卧推下次上 62.5kg，RIR 控制在 2–3。另外——你训练是在健身房还是家里？有器械清单我才能排得准。
② 破 PR 时（主动播报 + 下次建议）
你：卧推 62.5 5 5 5，最后一组还剩 1 个
教练：卧推 62.5kg×5 → 估 1RM 73.0kg，破 PR（上次 70.0，+3.0）。下周上 65kg，RIR 留 2–3；如果第 3 组掉到 4 次就别硬顶，退回 62.5 补次数。
③ 查 PR
你：我卧推到多少了
教练：卧推当前 1RM 估 73.0kg（09-09，62.5×5）。近三次：70.0 → 73.0，在涨。
指标现在v0.2.0 后
建议的个性化程度通用健身知识基于你自己的 PR 曲线与 RIR
进步的正反馈无破 PR 主动播报
下次练多少靠感觉有明确推导（重量/次数/RIR）
伤病规避被动（你提了才知道）档案里的禁忌动作长期生效

五、本次不做（明确边界）

不做原因

周复盘（容量/频率/停滞）P1，同上

体重体测趋势、血液指标P2–P3
动 life / mood本次范围只到 fitness

六、风险与已知边界

  1. 1RM 是估算值，不是实测，误差约 ±5%，只能看趋势、不能当绝对数字。回复里会带「估」字。
  2. 历史训练记录无法回溯生成 PR——之前 exercises 存的是字符串、无统一动作名与 RIR。PR 从 v0.2.0 上线后新记的开始积累。（可选：写一次性回填脚本，用正则从旧 raw_input 抽数字补建 PR。）
  3. 动作名归一靠 LLM 输出 + 包含匹配，同一动作的不同叫法可能被拆成两条 PR 曲线。用久了可在档案里维护别名表，本次不预先做。
  4. 档案为空期间建议会偏通用，这符合现有「不编造」约束，不是 bug。
  5. 新增抽取字段会让单次记录多耗少量 token，响应仍在秒级。
